# Memory / plans

Working notes for whoever (whatever) is building this, across runs. Not a changelog — update this in place, don't append entries.

## What this is

A collection of small, in-browser tools under one landing page ("open apps"), deployed to GitHub Pages. Each tool is its own SvelteKit route, self-contained, no backend, no accounts, no analytics. The site itself is deliberately under-branded for now — no persona name yet, no forced tagline beyond "small tools kept in your browser." Let a voice/name emerge through what gets built and (occasionally) written, rather than declaring one up front.

## Stack & conventions

- SvelteKit (Svelte 5, runes mode forced via `vite.config.ts`), TypeScript, `@sveltejs/adapter-static`.
- No `svelte.config.js` — kit config (adapter, `paths.base`) lives directly in the `sveltekit()` plugin call in `vite.config.ts`, since SvelteKit 2.62+. Don't add a separate config file; extend the existing object.
- GitHub Pages serves this repo at `/openapps/`. `vite.config.ts` reads `BASE_PATH` from env at build time; the `autodeploy.yml` workflow sets `BASE_PATH=/openapps`, local/CI-check builds leave it unset. Internal links use `resolve()` from `$app/paths` (or manual `{base}` + eslint-disable when the path is built dynamically from data, e.g. `AppCard.svelte`) — never hardcode `/apps/...` without one of these, or GH Pages links break.
- Prerendering is on globally (`src/routes/+layout.ts`). Every route should still work as a static export — no server-only APIs.
- Design system lives in `src/app.css` as CSS custom properties, light by default with a `prefers-color-scheme: dark` override. Warm off-white / near-black with one coral accent (`--accent`). System font stack only — no webfonts, no external requests, fits the "nothing leaves your device" ethos of the tools themselves.
- New tool checklist: add a route at `src/routes/apps/<slug>/+page.svelte`, add an entry to `src/lib/apps.ts` (name, tagline, description, tag, inline SVG icon), keep it fully client-side, give it its own small back-link to `/`.
- No emojis anywhere on the site (icons are hand-authored inline SVG).
- `localStorage` is fine to reach for when a tool's whole value is remembering something between visits (Meridian's saved zone list is the first case) — it never leaves the browser, so it doesn't break "nothing is ever uploaded." Default is still no persistence; only add it when resetting on reload would genuinely defeat the tool's purpose, not as a routine nicety.
- `npm run build` must pass before opening a PR — that's the automerge gate in `.github/workflows/automerge.yml`.
- **A merge does not automatically deploy — check that it did.** `autodeploy.yml` triggers on `push` to `main`, but automerge's squash-merge is pushed as `GITHUB_TOKEN`, and GitHub deliberately raises no `push` event for those (it's the loop guard). So an auto-merged PR historically never deployed; the daily 07:30 Europe/Warsaw cron was the only thing catching the site up, and two of the five deploy runs in the repo's history were somebody hand-firing `workflow_dispatch`. Fixed by adding a `workflow_run` trigger on the automerge workflow completing (that event is raised by the run finishing, not by its push, so it isn't suppressed), gated on `conclusion == 'success'`, with the checkout pinned to `ref: main` — on a `workflow_run` event the default checkout ref is the _triggering_ run's head SHA, i.e. the PR branch automerge has already deleted. If a future run needs the site live immediately anyway, `actions_run_trigger` → `run_workflow` on `autodeploy.yml` @ `main` works.
- **Branch names must start with `claude/`** (e.g. `claude/mat-screenshot-framer`). `automerge.yml`'s build-check job is guarded by `if: startsWith(github.head_ref, 'claude/')`, and the merge job is `needs: build-check` — a skipped dependency skips the merge too. So a PR from an unprefixed branch never gets a check and never merges, and there is **no failing status to notice**; it just sits open looking fine. This silently stranded PR #5 (and, judging by their timings, is probably why the Swatch and Sift PRs had to be merged by hand). Verified: the same commit re-pushed to `claude/mat-screenshot-framer` merged on its own within a minute.
- **Svelte 5 `$state` array gotcha (found while building Bare, also silently broke Squish's first-batch processing until fixed this run):** when you build a list of plain objects with `.map()` and _then_ assign it into a `$state` array (`items = [...items, ...newItems]`), the objects Svelte hands back when you later read `items` are reactive proxies — but a reference to one of those objects captured _before_ the assignment (e.g. the `newItems` array itself, or an `item` closed over in the `.map()` callback) is still the plain pre-proxy object. Mutating that reference (`item.status = 'done'`) changes the data but fires no signal, so the UI never updates — no error, no warning, it just silently sits at its initial state forever. Squish's `processItem`/Bare's `readItem`+`stripItem` all hit this on first upload (worked fine on any _later_ re-derivation from `items` itself, e.g. Squish's slider-triggered reprocessing, since that iterates the already-reactive array). Fix applied in both: mutator functions take an `id` and do `items.find((e) => e.id === id)` fresh, right before every mutation, instead of closing over an object handle. **Any new tool that builds a list of items to process asynchronously must follow this id-lookup pattern** — don't hand an object reference into an async function and mutate it later.
- Always smoke-test a new tool's actual async/upload flow with Playwright (not just `npm run check`/`build`) before shipping — type-checking and a successful build do not catch this class of bug, since the mutation is technically valid, type-correct JS that just doesn't reach the DOM.

## Built so far

- **Squish** (`/apps/squish`) — drag-and-drop image compressor/resizer, canvas-based (`src/lib/squish/compress.ts`), format auto/JPEG/WebP/PNG, quality slider, max-dimension presets, paste-from-clipboard support, per-file and batch download. Honestly reports when output is _larger_ than the source (can happen re-encoding already-optimized PNGs) instead of hiding it — worth keeping that honesty pattern in future tools rather than always claiming "savings." Fixed once already: `processItem` used to take the item object directly, which silently broke the _first_ batch of uploads (see the `$state` gotcha below) — now takes an `id` and looks the item up fresh from `items`.
  - **Redesigned later the same day: dropping a file used to compress it immediately, picking a format on the user's behalf.** Flagged directly: an image tool should let files pile up before committing to anything, default to keeping the source's own format (not silently converting it), and show what the alternatives would cost/save as a suggestion rather than deciding. Turned into a general principle worth keeping for any future tool shaped like this one: **live/instant preview stays the default everywhere it's non-destructive and reversible (Hue's picker, Bloom's gradient, Swatch's palette) — the exception is an action that produces a final artifact with a choice baked in the user didn't consciously make, which is what auto-compress-on-drop actually was.** Concretely: items now land with `status: 'pending'` and nothing runs until an explicit `Compress N image(s)` button click (which also handles *re*-compressing already-`done` items if settings changed after the fact — one button, not a stale/fresh distinction to track); the format `$effect` that used to auto-rerun compression on every quality/format/size tweak is gone entirely. `format: 'auto'` was already resolving to the source's own type when supported (`resolveFormat` in `compress.ts`) — the actual bug was auto-running at all, not the default being wrong, so that logic didn't need to change. New: a per-format size *estimate* panel (Auto/JPEG/WebP/PNG, each shown as a clickable card that just sets `format` — the suggestion is one click from being acted on, never applied on its own), computed against whichever pending file is largest since that's the one most likely to actually matter for the decision. This estimate **does** update live as quality/size change, deliberately — it's read-only preview info that never produces a downloadable artifact or touches `item.status`, so it's exactly the kind of "instant feedback is fine" case the principle above carves out, not an exception to it. Verified the estimate and the real compress path agree exactly (clicked "WebP" in the estimate panel showing 3.3 KB, then compressed, got 3.3 KB) — same `compressImage` call underneath both, so this is a genuine consistency guarantee, not a coincidence to reverify by hand later. Also retrofitted onto `ToolHeader`/`Button`/`Panel` while already deep in this file for the behavior change — opportunistic, not a dedicated retrofit pass, but a reasonable way to make progress on that sweep without a separate PR every time.
- **Bare** (`/apps/bare`) — hand-rolled JPEG EXIF/GPS reader and stripper (`src/lib/bare/exif.ts`), no dependency. Parses IFD0/Exif/GPS IFDs directly from a `DataView` and shows camera make/model, timestamps, exposure settings, and decimal GPS coordinates (with an explicit, user-clicked OpenStreetMap link — never auto-loaded). Stripping rewrites the JPEG segment structure to drop all APPn/COM segments and copies the compressed scan data through byte-for-byte — no canvas re-encode, so zero quality loss, unlike Squish; verified with Pillow that a stripped file decodes to pixel-identical output with an empty EXIF dict. Distinguishes "no metadata at all" from "no camera/GPS fields, but some container housekeeping bytes (e.g. a bare JFIF `APP0` marker) present" — collapsing those into one "already clean" message would have been dishonest, since the strip button still has something to do in the second case. First tool tagged `Privacy` instead of `Images`; the landing page doesn't group by tag yet but the field is there for when it's worth it. Introduced `src/lib/format.ts` for the shared `formatBytes` — Squish's copy in `compress.ts` was left as-is rather than refactored, to avoid touching a working, previously-reviewed file for a minor DRY nit.
- **Swatch** (`/apps/swatch`) — dominant-color palette extractor (`src/lib/swatch/palette.ts`), no dependency. Downscales the image onto a small offscreen canvas (max 120px side) and runs classic median-cut quantization on the sampled pixels, splitting the widest-range bucket in half by median until it has as many buckets as the "colors" slider asks for (3–10, shared across the whole batch like Squish's quality slider). Each swatch shows hex/RGB/share-of-image, click-to-copy any swatch, "Copy as CSS" emits `:root { --swatch-N: #hex; }`. Text color per swatch picked via WCAG relative luminance so labels stay legible on both light and dark fills. Third tool tag, `Design`. **Bug caught by the Playwright smoke test, not by build/check**: median-cut would keep splitting a bucket even once it had zero color range (e.g. a solid-color background/quadrant), producing two buckets that average to the identical rounded hex — Svelte's `{#each ... (color.hex)}` then threw `each_key_duplicate` and crashed the results panel. Fixed two ways: (1) `medianCut` now only splits a bucket whose widest-channel range is `> 0`, so a genuinely flat region stops splitting instead of manufacturing a fake duplicate; (2) `buildPalette` also merges any buckets that still land on the same hex after rounding, summing their population — belt-and-suspenders, since floating-point rounding could in principle produce a second collision some other way. Net effect: asking for more colors than an image actually has just honestly returns fewer swatches, same honesty pattern as Squish's "larger" label and Bare's "already clean" distinction. Computed a `displayItems` derived value (`item + colors`) instead of caching `.colors` on each item via `$effect` — keeps recomputation a pure function of `items`/`colorCount` and sidesteps the `$state`-array mutation gotcha below entirely for this tool (only `readItem`'s async decode step needed the id-lookup pattern).
- **Sift** (`/apps/sift`) — first non-image tool, first `Dev` tag. JSON formatter/validator + structural diff, no dependency, text-in/text-out instead of files. `src/lib/sift/json.ts` parses and, on a `SyntaxError`, turns the engine's message into a line/column pointer — handles both V8's `"position N"` and Firefox's `"line L column C"` formats, since the two browser engines report JSON errors completely differently and testing only in Chromium would have missed that. `src/lib/sift/diff.ts` does a structural deep diff (object keys by name, arrays by index — positional, not an LCS/Myers diff, so an insertion at index 0 shows every later index as "changed" rather than reordered; noted in a comment, not hidden) and produces a single `DiffNode` tree shape that both modes render through one component, `src/lib/components/JsonNode.svelte`: Format mode wraps a plain value as an all-`unchanged` tree (`toPlainTree`) so it reuses the exact same collapsible-tree renderer as Diff mode instead of a second bespoke view. `JsonNode` recurses via a self-import (`import Self from './JsonNode.svelte'`) rather than `<svelte:self>` — works fine on Svelte 5. Collapse state is a path-keyed `SvelteSet` (from `svelte/reactivity`) held in the page, not local `$state` in each node — a plain `Set` mutated in place wouldn't trigger reactivity without reassignment, and `SvelteSet` sidesteps that. Diff coloring intentionally breaks from "one coral accent only": added/changed get two new page-scoped CSS vars (`--diff-add` green, `--diff-changed` amber, both with dark-mode overrides) defined on `.page` and inherited down into `JsonNode` via normal CSS custom-property cascade (Svelte scoping doesn't block that) — removed reuses the existing `--accent`, since that's already the site's "attention" color elsewhere (Bare's/Swatch's `.status.error`). Conventional add/remove/change colors are load-bearing for a diff tool's usability in a way the single-accent rule wasn't designed around; kept the deviation scoped to this one page rather than touching `app.css`. Also widened this page's own `max-width` to `60rem` (others are `42rem`) since two side-by-side JSON editors need the room; a page-local override, not a global change. `--diff-add`/`--diff-changed` and the wider max-width are precedents if a future tool needs the same.

- **Mat** (`/apps/mat`) — screenshot framer: mounts an image on a background with padding, rounded corners, shadow, optional window bar, and exports PNG at 1×/2×/3×. `src/lib/mat/render.ts` holds all the drawing; `renderMat(canvas, bitmap, opts, scale)` **sizes the canvas itself and is used for both the live preview and the export**, so what you download is provably what you were looking at — the only difference between the two calls is `scale`. Layout math (`computeLayout`) is a separate pure function so the page can show the export dimensions without drawing anything. Ratio presets only ever _grow_ the canvas to reach a shape, never crop the image — stated in the UI, same honesty pattern as the other tools. First tool with a single-image editor shape (Squish/Bare/Swatch are batch lists), which was a deliberate change of pace. Notable bits: (1) rounded rects are hand-rolled with `arcTo` rather than `ctx.roundRect`, so old WebViews don't silently lose corners; (2) grain is a cached 128px mid-grey noise tile composited with `overlay` and painted with the transform **reset to identity**, so it stays fine texture at 3× instead of scaling into visible blocks; (3) the "Image" background reuses Swatch's `buildPalette` but picks the most _saturated_ prominent color, not the most common one — screenshots are mostly white/grey by area and the literal dominant color makes a white-on-white non-background — and falls back to a warm neutral when the image is genuinely near-greyscale (`s < 6`) rather than inventing a random hue; (4) the checkerboard lives on the `<canvas>` element's own background, not the stage around it, so it only ever means "this part of the export is transparent." **Reactivity pattern worth reusing:** the background isn't stored in the bound `opts` object — it's derived (`settings = $derived({ ...opts, background: activeBackground })`) so no `$effect` ever writes back into state; the render effect is the only effect, and it just draws. Page `max-width` is `62rem` (Sift's `60rem` precedent).

- **Folio** (`/apps/folio`) — first `Docs`-tagged tool, first pure-text (non-JSON) writing tool. `src/lib/folio/markdown.ts` is a hand-rolled, dependency-free Markdown → HTML renderer (~500 lines): a line-based block parser (headings, paragraphs, fenced code, blockquotes, ordered/unordered lists with indentation-based nesting, GFM tables, thematic breaks) feeding a small recursive-descent inline parser (bold/italic/strike/code spans/links/images/autolinks). Deliberately a pragmatic subset, not full CommonMark — no setext headings, no reference-style links, no raw HTML passthrough (any literal `<...>` in the source is escaped, never executed — the file's top comment states this explicitly), and the emphasis scanner's simple delimiter matching (vs. CommonMark's full delimiter-run algorithm) doesn't resolve combined `***bold italic***` correctly, documented in the same comment rather than silently producing wrong output. Two-pane editor/live-preview layout; "Download HTML" wraps the render in a self-contained styled document (`src/lib/folio/document.ts`, inlined CSS, fixed warm-light theme so it looks right opened cold in any browser) and "Print / Save as PDF" just calls `window.print()` over a `@media print` stylesheet scoped to the preview pane — no PDF-writing code needed, the browser already knows how. **Playwright smoke-testing caught two real parser bugs a build/type-check couldn't**: (1) the paragraph-continuation loop didn't treat a new list-marker line as a block boundary, so a bullet list nested under an ordered item was silently absorbed as plain paragraph text instead of parsing as a nested `<ul>` — fixed by adding the list regexes to the same break condition already used for headings/rules/fences/quotes; (2) the table-delimiter regex required 2+ dashes per cell (`-{2,}`), silently rejecting the very common single-dash/colon delimiter forms (`|-|`, `|:-:|`) and falling back to rendering the whole table as one flat paragraph — fixed to `-+`. Also hit a **Svelte scoped-CSS gotcha specific to print stylesheets**: a "hide everything, then un-hide `.printable`" approach via `:global(body) *` doesn't actually reach elements owned by a _different_ component (here, `+layout.svelte`'s header/footer) — Svelte only unscopes the part of the selector literally inside `:global(...)`, so a trailing bare `*` still gets this component's own scope class appended and only ever matches this component's own markup. Fixed by listing exactly what to hide instead: `:global(header)`/`:global(footer)` (fully global, no trailing compound selector) plus this page's own classes (`.back`, `.intro`, `.toolbar`, `.editor-panel`, `.panel-header`), with `!important` on the header/footer rule since the layout's unconditional `display: flex` has equal specificity and can otherwise win the cascade depending on stylesheet link order. Worth remembering for any future tool that wants a print or "hide the chrome" view — target another component's elements with a fully-global selector, never assume `:global(ancestor) descendant` unscopes the whole chain. Also a reminder for testing itself: after rebuilding mid smoke-test session, the running `vite preview` server must be restarted — it doesn't pick up new hashed asset filenames from a rebuild that happened after it started, and the resulting stale/missing-chunk 404s masquerade as a hydration race (looked exactly like Playwright's `.fill()` on the textarea being silently reverted) rather than an obviously-stale-server problem.

- **Beacon** (`/apps/beacon`) — QR code generator, first `Share`-tagged tool. `src/lib/beacon/qr.ts` is a from-scratch ISO/IEC 18004 (QR Model 2) encoder, ~600 lines, no dependency: mode selection (numeric/alphanumeric/byte, single segment — no multi-segment splitting, documented in the file's top comment as a deliberate simplification), Reed–Solomon error correction over GF(256) built from a primitive-polynomial exp/log table, and full module placement (finder/timing/alignment patterns, zigzag data placement, all 8 mask patterns scored via the standard four penalty rules with the lowest-penalty mask chosen). Format info (15 bits) and version info (18 bits, versions 7+) use hardcoded lookup tables (32 and 34 entries respectively, fetched from a reference source) rather than a runtime BCH implementation — fewer moving parts to get wrong than deriving the polynomials live, and small enough tables to just be correct. Same for the big per-(version, EC-level) error-correction block-layout table (160 entries, `EC_TABLE`) and the alignment-pattern coordinate table (versions 2–40) — both transcribed from a reference source and then verified programmatically (block-count × size sums match the stated totals for all 160 entries).
  - **This one got a real correctness scare that turned out to be a false alarm, worth remembering the debugging path.** Initial fuzz testing (piping generated codes through Python's `cv2`/`pyzbar` QR decoders) showed every code containing accented/multi-byte characters (ö, é, €, — etc.) coming back corrupted, which looked exactly like a byte-mode encoding bug. Chased it through three levels of increasing rigor: (1) an in-process bit-exact round-trip — re-deriving the same zigzag module order used for placement, reading bits back out of the generated matrix, de-masking, and comparing against the actual codewords `buildCodewords` produced — passed 160/160 with zero mismatches, proving the matrix embedding was exactly right; (2) cross-checking with OpenCV's `QRCodeDetector` (not zbar) showed the _same_ strings decoding correctly, byte-for-byte; (3) zbar/pyzbar was the odd one out, consistently mis-transcoding multi-byte UTF-8 in byte-mode segments with no ECI designator — a known zbar charset-guessing quirk, not a bug in the generated code. Real-world scanners (iOS/Android camera apps, most modern QR generators including zxing) assume UTF-8 for byte-mode with no ECI by convention, same as what this encoder emits; adding an explicit UTF-8 ECI designator would only _hurt_ compatibility with simpler scanners that don't parse ECI at all. **Lesson for verifying any future from-scratch binary-format tool: when a supposedly-authoritative test oracle disagrees with your own logic, don't trust the oracle by default — cross-check against a second independent oracle before believing you have a bug.** One flaky/quirky decoder produced what looked like damning, systematic evidence; a second one (plus an in-process ground-truth check that doesn't depend on any external tool at all) showed the first one was wrong.
  - Verification, end to end: a Playwright smoke test filled the real page's textarea, clicked "Download PNG" to get the actual browser-rendered file (canvas → `toBlob`, not a Node reproduction), and decoded it with pyzbar — came back byte-exact as the original URL. Also exercised the low-contrast warning (visibly correct, faint code rendered exactly as the contrast math said), the "text too long for this EC level" error state, dark mode, and 390px mobile.
  - `src/lib/beacon/render.ts` holds `renderToCanvas` (draws to a canvas sized from matrix size + quiet zone + scale) and `toSvgString` (run-length-encodes each row into `<rect>` elements rather than one `<rect>` per module — meaningfully smaller markup, and it's what most SVG QR generators do). `contrastRatio` reuses the same WCAG relative-luminance formula as Swatch's `textColor` pick, exposed here as an honest, non-blocking warning ("contrast below ~4.5:1 can be unreliable to scan") rather than a hard block — same pattern as Squish's "output is larger" and Bare's "already clean" distinctions: tell the truth, let the user decide.
  - Quiet zone is fixed at the spec-minimum 4 modules, not a control — same "three controls and done" instinct as Mat. PNG export offers a px/module choice (6/10/16); SVG is offered unconditionally since it's resolution-independent and arguably the _better_ default for a QR code, but PNG stays primary since that's what most people expect to paste into a doc or slide.
  - `QrMatrix`'s success case carries `ok: true` (and `CapacityError` carries `ok: false`) specifically so `result.ok === false` narrows cleanly in the Svelte template — discovered mid-build that a type without a shared discriminant field forces awkward `'in'` checks everywhere it's read.

- **Loop** (`/apps/loop`) — video-to-GIF trimmer, first `Video`-tagged tool. `src/lib/loop/gif.ts` is a from-scratch GIF89a encoder (~200 lines, no dependency): header, logical screen descriptor, one global color table, a NETSCAPE2.0 application extension for infinite looping, and per-frame graphic control + image descriptor + LZW-compressed indexed data. `src/lib/loop/quantize.ts` builds one shared palette across every sampled frame (median-cut, same family of algorithm as Swatch's, kept as a separate self-contained copy since this version pools samples across time and needs an index-map step Swatch never does) and maps pixels to palette indices with a color→index cache (video frames are full of repeated colors, so most pixels are cache hits instead of a fresh nearest-neighbor search). `src/lib/loop/capture.ts` samples a trimmed video range by seeking an `HTMLVideoElement` and drawing each stop to a scaled offscreen canvas — deliberately not `requestVideoFrameCallback` (not implemented everywhere) and seek accuracy is more than enough for a GIF's own coarser frame rate anyway. UI follows Mat's single-editor shape: drop a video, `Mark start`/`Mark end` buttons capture the native `<video controls>` playhead into the trim range (plus fine-tune range sliders), segmented pills for fps/width/color-count, and an honest hard cap — 360 frames — that disables Generate with an explicit message instead of ever silently truncating or hanging on a huge export.
  - **Verification, in three independent layers, because a hand-rolled binary encoder is exactly the class of bug that build/type-check can't catch (same lesson as Beacon).** (1) Bit-exact unit tests via `tsx`, run directly against `gif.ts`/`quantize.ts` with zero DOM: an exact-color checkerboard decoded pixel-for-pixel correct across 3 frames, a 120×90/6-frame/128-color stress case, a worst-case 200×150 fully-random-pixel frame (forces LZW dictionary resets mid-frame, the hardest path to get wrong), and a solid-color 1-palette-entry edge case — all decoded with Python's PIL (an independent, real-world GIF decoder, not a hand-rolled check that could share the same misunderstanding of the spec) and matched expected pixels/frame count/loop flag/durations exactly. (2) A full Playwright end-to-end run against the actual built site: recorded a real ~20s animated video in-page via `canvas.captureStream()` + `MediaRecorder` (so the test exercises real video decoding, not a mocked file), fed it into the real dropzone, drove the real trim/fps/width/color controls, clicked the real Generate button, and fetched the resulting `blob:` URL's bytes directly — the literal bytes a user's download would contain — then re-verified those with PIL too (frame count, dimensions, loop, color budget). Also confirmed the 360-frame budget genuinely blocks Generate (not just cosmetically) when trim+fps overshoot it, and that narrowing the range clears the warning. Ran at both a 1280px desktop and 390px mobile viewport with a `pageerror`/console-error listener attached — clean both times. (3) Rendered actual output frames back to PNG and eyeballed them against the known synthetic source (a hue-cycling background with a moving white dot) to catch anything structurally "valid" but visually wrong that an automated pixel-count check might miss.
  - **Two real browser quirks hit and fixed, not testing artifacts — both apply to real user-supplied files, not just the synthetic test video:** (1) MediaRecorder-produced containers (webm from phones/screen-recorders, not just this tool's own test fixture) commonly report `video.duration` as `Infinity`/`NaN` until you seek near the end once — worked around in `onLoadedMetadata` by seeking to a huge timestamp, waiting for `timeupdate`, then seeking back to 0, before reading the now-correct duration. (2) TypeScript's newer generic `Uint8Array<ArrayBufferLike>` vs `Uint8Array<ArrayBuffer>` distinction (introduced for the shared-buffer split) made a plain `Uint8Array` return-type annotation on `encodeGif`/`ByteWriter.toUint8Array` reject assignment into `Blob`'s `BlobPart`; fixed by annotating the concrete `Uint8Array<ArrayBuffer>` instead of the bare (defaults-to-`ArrayBufferLike`) alias — worth remembering for any future function that builds a `Uint8Array` for a `Blob`/`fetch` body with an explicit return-type annotation, since Bare's `exif.ts` never hit this only because its return type was left to inference.
  - Colors budget check is a hard block (disabled Generate button + inline message), same "tell the truth, don't silently clamp or truncate" pattern as everywhere else on the site (Squish's size-larger-than-source label, Beacon's capacity error, the bento grid's no-silent-crop rule).

- **Crest** (`/apps/crest`) — favicon/site-icon package generator, first `Web`-tagged tool. Drop in a logo and it center-crops to a square (never stretches — same honesty instinct as Mat's ratio presets), composites over a transparent or solid background with adjustable padding, and packages `favicon.ico`, `favicon-16x16.png`, `favicon-32x32.png`, `apple-touch-icon.png`, two `android-chrome-*.png` sizes, `site.webmanifest`, and a `head-snippet.txt` into one ZIP — the standard modern favicon set, no signup, no ad-supported generator site. Two from-scratch binary encoders, no dependency: `src/lib/crest/zip.ts` (PKZIP local headers + central directory + EOCD, store/no-compression method — a favicon package is a handful of small files, not worth a DEFLATE implementation) and `src/lib/crest/ico.ts` (ICONDIR + ICONDIRENTRY wrapping plain PNG bytes — Vista+ and every current browser accept PNG-in-ICO directly, so no BMP/AND-mask encoding needed). `src/lib/crest/render.ts` holds the one shared `renderIcon(canvas, bitmap, size, opts)` used for the live preview and every exported size alike (same "the download is provably what you saw" pattern as Mat's `renderMat`); PNG bytes themselves come from the browser's own `canvas.toBlob`, not a hand-rolled encoder — no reason to reimplement PNG when every tool on this site already trusts the platform encoder for that format.
  - **Real correctness point, not just an edge case: iOS renders any transparent pixel in a home-screen icon as solid black** — there's no checkerboard fallback like a browser tab gets. `renderIcon`'s `opaqueFallback()` helper forces a white background specifically for the Apple touch icon render when the user picked "Transparent," while every other output (favicon PNGs, the ICO, the Android manifest icons) stays genuinely transparent if that's what was asked for. The UI states this explicitly next to the background toggle rather than silently changing one file and not the others. - **Delta** (`/apps/delta`) — plain-text/code diff tool, second `Dev`-tagged tool (after Sift, which only diffs JSON structurally — Delta works on any text: code, config, prose). `src/lib/delta/diff.ts` is a from-scratch Myers' O(ND) shortest-edit-script implementation, generic over arrays of any comparable item — used once for line-level diffing (`text.ts`'s `diffLines`) and again for word-level diffing within a single changed line (`wordDiff`, tokenizing on whitespace-run/non-whitespace-run boundaries so highlights land on whole words, not characters). `rows.ts` groups the flat edit script into display rows, pairing up a run of consecutive deletes with a run of consecutive inserts (index-wise, up to the shorter run's length) into `replace` rows eligible for word-level highlighting — a leftover uneven tail stays a plain delete/insert rather than a fake pairing, same honesty instinct as everywhere else on the site. A signature check is exactly the kind of security-critical code this site shouldn't be the one to get subtly wrong, and the platform already has an audited one. What *is* hand-written: `src/lib/claim/base64url.ts` (base64url encode/decode via `atob`/`btoa`, since there's no Buffer in a browser), `jwt.ts`'s parsing/signing-input construction, and `pem.ts`'s PEM-armor stripping to feed `importKey('spki', …)`.
  - **Verification only ever asks for a public key, deliberately, and the doc comment in `verify.ts` says why.** RS*/ES* verification takes a PEM public key, never a private key — there's no legitimate reason a signature-verification tool would want one, and offering to accept one would invite a real credential to be pasted into a browser tab. Encode mode covers "I need to sign something real" for HS256/384/512 only (a shared test secret, not a keypair) — asymmetric signing needs a private key and deliberately isn't offered at all, not even as an unimplemented button.
  - **A real correctness lesson, caught before it shipped, not after:** ECDSA's Web Crypto signature format is raw `r||s` concatenation (no ASN.1 DER wrapping) — which happens to be exactly what JOSE/ES256 already uses, so no signature re-encoding step was needed. This *looked* like it might need one going in (most ECDSA APIs — including Node's `crypto.sign` by default — produce DER-wrapped signatures) and was confirmed against the Web Crypto spec text before writing the verify path, rather than assumed and found broken later by a test.
  - **`alg: "none"` gets its own always-shown warning banner, not folded into the expiry/verify UI** — a token with no signature at all is a well-known JWT vulnerability class (anyone can forge arbitrary claims by stripping the signature and setting this field), and the banner says so explicitly rather than just silently offering no verify input. Same "tell the truth about what's insecure" instinct as the rest of the site's honesty patterns, aimed here at the user's *security* rather than a tool's output quality.
  - Claims table shows RFC 7519's standard registered claims (`iss`/`sub`/`aud`/`exp`/`nbf`/`iat`/`jti`) with human labels and, for the three time claims, both an absolute (`toLocaleString`) and relative (`Intl.RelativeTimeFormat`) rendering — then any custom claims after, in the payload's own key order (never alphabetized, since a token's own claim order sometimes carries meaning). Expiry status is a three-way honest state (valid / expired / not-yet-valid via `nbf` / no expiry claim at all), refreshed every 15s via a `setInterval` inside an `$effect` so "expires in 3 minutes" actually counts down while the tab sits open rather than freezing at parse time.
  - The "Load sample" button doesn't embed a precomputed token string — it calls the page's own `encodeJwt` live, with a payload whose `exp` is deliberately 1 hour in the past (`now - 3600`). This makes the demo self-verifying (if encode/decode/verify didn't agree, the sample wouldn't show "Signature valid") and, as a side effect, demonstrates an important distinction up front: a token can have a perfectly valid signature and still be expired — two independent checks, not one pass/fail.
  - **Verification, in two layers, going further than "does it look right in the browser" because signature verification is the one place a subtle logic bug reads as silently insecure rather than visibly broken.** (1) A full Playwright pass against the real built site — load sample → signature valid; hand-edit one payload byte → signature invalid; malformed token (wrong part count) → error; `alg: "none"` → warning banner, no key input rendered at all. (2) Independent cross-checks against Node's own `crypto` module, not just internal consistency: generated a real RSA-2048 keypair and a real P-256 EC keypair with `crypto.generateKeyPairSync`, signed test payloads with the *private* keys (`dsaEncoding: 'ieee-p1363'` for the EC case, to get the raw r||s format JOSE needs), pasted the *public* key PEM into the real page, and confirmed Claim's `crypto.subtle.verify` call reports "Signature valid" for the correct key and "Signature invalid" for a different, wrong key of the same type — proving the PEM-to-SPKI import and verify wiring is correct against real external keys, not just tokens the tool made for itself. Separately, byte-exact-compared an Encode-mode-generated HS384 token against an independently computed `crypto.createHmac('sha384', secret)` over the same signing input in Node — exact match, confirming `base64url.ts` and the signing-input construction are bit-correct. Ran across 1280px light, 1280px dark, and 390px mobile with a `pageerror`/console-error listener attached throughout — clean. Landing page: confirmed the `Dev` filter pill now shows Sift, Delta, and Claim, and the card click-through navigates correctly.

- **Meridian** (`/apps/meridian`) — timezone/world-clock overlap tool, first `Time`-tagged tool and the **first tool on the site that persists anything to `localStorage`** (`src/lib/meridian/storage.ts`, a saved list of IANA zone ids under `meridian:zones`). Deliberate first: a saved team/travel zone list is the actual point of a world clock, unlike every other tool here being a one-shot editor that's fine resetting on reload — and localStorage never leaves the browser either, so it doesn't compromise the "nothing is ever uploaded" line, just extends "stays in your browser" from *this session* to *this browser*. All timezone math goes through `Intl` (`src/lib/meridian/tz.ts`) rather than a bundled tz database — first tool to deliberately *not* hand-roll something it plausibly could have, since every evergreen browser already ships full IANA tz data via ICU and there's no honest reason to duplicate it (same "trust the platform" call as Claim trusting Web Crypto, Crest trusting `canvas.toBlob`). One shared home-referenced 24-column axis: every zone row is the *same* 24 hourly columns (anchored to `homeMidnightInstant`, the detected local zone's midnight-today converted to a UTC instant via the standard "format both as naive UTC millis, diff for the offset" trick), each column re-labeled per row via `Intl.DateTimeFormat` — not per-row independent 24-hour strips — so a single draggable vertical cursor spanning all rows always points at one real, shared instant, and every row's shading/clock/date is a pure function of that instant.
  - **A real CSS Grid bug, not a Svelte one, and worth remembering generally.** The vertical drag-cursor overlay was given `grid-row: 1 / -1` to span the ruler-plus-every-zone-row region of an implicit-row grid (no `grid-template-rows` was ever set — rows were left to auto-placement). It rendered at **zero height** — not visually broken, structurally invisible, so dragging silently did nothing (`getBoundingClientRect().height === 0`) with no console error and no obviously-wrong pixels to eyeball. Root cause, confirmed by boundingBox() logging in a Playwright debug script before landing on the theory: per the Grid spec, a negative line index like `-1` counts back from the **explicit** grid's line count, and a grid with no `grid-template-rows` has an explicit row count of essentially zero/one — so `1 / -1` collapsed instead of spanning the real (implicit) row count. A first, wrong fix attempt was removing an `align-items: center` from the grid container (that was a real but *separate* bug — it was independently collapsing the same element by centering it around zero intrinsic content height — fixing it alone still left height at 0, which is what pointed at a second, distinct cause rather than declaring victory early). The actual fix: stopped relying on row-spanning at all — `.grid-wrap` got `position: relative` plus two CSS custom properties (`--head-w`, `--gap-x`) shared with the column template, and the overlay became `position: absolute; top/bottom: 0; left: calc(var(--head-w) + var(--gap-x)); right: 0`, sized purely from the container's own content height regardless of row count. **General lesson: a grid item meant to span "all rows" of a container with implicit (auto-placed) rows should not use `grid-row: 1 / -1`** — either declare `grid-template-rows` explicitly first, or (usually simpler, as here) pull that element out of grid flow entirely with `position: absolute` inside a `position: relative` grid container.
  - **A real ECMA-402 data quirk, caught by a Playwright test using "Kolkata" as a search fixture and failing to find it.** `Intl.supportedValuesOf('timeZone')` — standardized, present in every current evergreen browser, not a Chromium-specific or stale-test-fixture artifact — still returns `Asia/Calcutta`, `Asia/Rangoon`, `Asia/Saigon`, and `Europe/Kiev` as the *canonical* ids for Kolkata, Yangon, Ho Chi Minh City, and Kyiv; the canonicalization table hasn't caught up to those renames even though the underlying IANA tzdata has long treated the modern spelling as primary. Confirmed this wasn't a test-environment artifact by checking the actual Chromium version in use (141, current as of this run) before concluding it was a genuine, live quirk rather than something to shrug off. Fixed with a small `CITY_OVERRIDES` map in `zoneLabel()` that substitutes the modern display name for exactly those four ids — search still matches on the *raw* id too (so typing either "Kolkata" or "Calcutta" finds it), only the shown label and the copy-summary text change; the actual `Intl` calls underneath (offset, wall time, DST) always use the untouched raw id, since that's the only string `Intl` itself actually accepts. **Lesson for any future tool that surfaces IANA zone names to a general audience: don't assume the platform's own "canonical" spelling is the one a user would type or expect to read** — cross-check a handful of well-known renamed cities before shipping a location picker, the same instinct as verifying a hand-rolled format against an independent oracle, just applied to a *data quality* question instead of a correctness one.
  - Day/night shading (`bandForHour` → `day`/`twilight`/`night`, computed per hourly column per row via `daySegments`) deliberately stays inside the site's existing monochrome palette instead of introducing a blue "night sky" — `color-mix(in srgb, var(--text) N%, var(--bg))` at two strengths, so a band reads as "how much this hour leans toward the text/dark end of the theme" and the light/dark mode override is free: night is *always* the band closer to the theme's own dark end, day the band closer to its light end, in both color schemes, without a single band-specific dark-mode override needed anywhere.
  - Cursor has two states, not one: the solid accent-colored draggable line (`cursorFrac`, drives every row's displayed clock) and, only when it's been dragged away from live, a fainter dashed "now" marker (`liveFrac`) at its actual current position — same "don't let a paused/overridden value quietly hide where reality actually is" instinct as Splice's clipping flag or Beacon's contrast warning, just applied to *time* instead of *audio/image output*. A visible "Jump to now" button (and the `Home` key on the focused track) is the only way back to live-following; the state doesn't silently resume on its own, since a silently-resuming cursor mid-comparison would undo whatever the user just dragged to look at.
  - 12h/24h is a real toggle (segmented control, same visual pattern as Seal/Sift's mode switches) rather than picked once from locale — a world clock's whole audience is "people coordinating with people," and which clock format reads naturally is a personal/regional habit `Intl`'s locale guess doesn't reliably get right for the *other* person's convention, not just the visiting user's own.
  - Zone search matches `city`/`region`/`id` substrings (case-insensitive, top 8 results) against the full `listTimeZones()` list — no fuzzy matching, no ranking beyond "first 8 in list order," consistent with the rest of the site not reaching for a matching library where a plain `.includes()` is honest and sufficient at this data size (~400 zones). A curated ~35-zone `FALLBACK_ZONES` list covers browsers without `Intl.supportedValuesOf` (Safari < 15.4) — smaller, not broken.
  - Verified via a full Playwright pass against the actual built/previewed site, both the interaction test and a visual screenshot pass, across desktop light/dark and 390px mobile: add/remove zones through the real search dropdown, 12h↔24h toggle actually changing the displayed clock text, drag-to-preview showing/hiding "Jump to now" correctly, "Copy times" landing real multi-line clipboard content, and — the one persistence-specific check no other tool on this site needed — a real page reload confirming the saved zone list survives it. Clean `pageerror`/console-error listener throughout. Mobile also got a small follow-up fix after the first screenshot pass showed "New York" truncating to "New …" in the narrow head column: the `home` badge now wraps under the city name instead of competing for the same line under 30rem, and the city label switches from ellipsis-truncated single-line to a normal two-line wrap at that width — day/night labels landed correctly is one thing, but a truncated city name defeats the point of a *world* clock, so this got fixed rather than left as an acceptable-looking screenshot.

- **Ward** (`/apps/ward`) — password/passphrase generator, second `Security`-tagged tool after Seal. Two modes (segmented toggle, same pattern as Sift/Seal): character-based passwords (length 8–64, per-type toggles for lower/upper/digits/symbols, optional look-alike exclusion, optional "require at least one of each selected type") and diceware passphrases (3–10 words, separator choice, capitalize toggle, optional trailing two-digit number) drawn from `src/lib/ward/wordlist.ts` — EFF's public 7,776-word (`6^5`) diceware list, fetched directly from `eff.org` rather than a GitHub mirror (the couple of GitHub mirrors tried 404'd; the source itself served it fine) and committed verbatim as a plain array, ~7,776 unique lowercase words including a few genuinely-distinct hyphenated pairs (`yo-yo` vs `yoyo` are both real, separate entries — not a scraping bug).
  - **Never `Math.random`, anywhere in the file — first tool where that distinction is the entire point, not an incidental implementation detail.** `src/lib/ward/generate.ts`'s `randomInt(maxExclusive)` draws from `crypto.getRandomValues(Uint32Array)` with rejection sampling (redraw whenever the value lands in the short leftover slice above the largest exact multiple of `maxExclusive`) rather than a plain `% maxExclusive`, so no remainder is ever even slightly overrepresented — worth promoting as the default pattern for any future tool that needs a uniform random integer from a range that doesn't evenly divide 2^32, not just a nicety specific to this one.
  - **"Require at least one of each selected character type" is enforced by rejection sampling on the whole candidate, not by fixing specific positions.** A first-instinct implementation (guarantee slot 0 is uppercase, slot 1 is a digit, etc.) would leak structure and make the reported entropy an overstatement of the real thing; instead `generatePassword` draws a fully random string from the combined pool and only keeps it if it happens to already satisfy the constraint, discarding and redrawing otherwise (capped at 1000 attempts, unreachable in practice at any length this UI allows) — every *qualifying* string stays exactly as likely as every other one, so the reported entropy (`length × log2(poolSize)`, ignoring the tiny reduction the constraint technically implies) is an honest, very close approximation rather than a number the generation process actually contradicts.
  - Entropy/strength/crack-time all live as pure functions in `generate.ts`, independent of character positions or word choices — `strengthOf` buckets bits into five labels (Very weak → Very strong), `estimateCrackTime` runs one explicit, stated assumption (10 billion guesses/second, "a fast offline attack") through `2^bits / rate / 2` and formats it in human units up to a `10^N years` fallback for anything past the trillions — and the UI states the assumption in a visible caveat line rather than presenting the estimate as authoritative. Same honesty pattern as Splice's clipping flag and Beacon's contrast warning, applied to a number that's inherently a rough illustration rather than a measurement.
  - **Deliberately does not persist anything, breaking from the site's own localStorage precedent (Meridian) on purpose.** A saved password/passphrase history is exactly the kind of "remembering something between visits" that would make the tool *less* trustworthy, not more convenient — the opposite of Meridian's saved zone list, which is genuinely safe to keep around. Regenerating (the "New" button) increments a plain in-memory nonce that a `$derived.by` reads alongside the current options, so a fresh draw happens on click even when no option actually changed — nothing about a previous draw is kept once superseded, and nothing survives a reload at all.
  - Symbol charset (`!@#$%^&*()-_=+[]{};:,.<>/?`) deliberately excludes quotes, backslash, and backtick — the characters most likely to need escaping wherever the output actually gets pasted (a shell, a CSV, a URL, a JSON string) — a stated, documented choice rather than an arbitrary omission.
  - Icon is a padlock (shackle arc + body + keyhole) — checked against Seal's `#` and Crest's shield-plus-checkmark before committing to it, since Crest's icon was already changed once this repo's history for being too close to a different tool's shape; a padlock reads as "generates something that locks," distinct from both.
  - Verified via a full Playwright pass against the actual built/previewed site (not just build/`svelte-check`, same standing practice as every other tool here): default password generation and length; clicking "New" changes the value; a real clipboard copy round-trips byte-for-byte; unchecking every character type shows the empty-state message instead of crashing; excluding look-alikes at an 8-character lowercase-only length actually produces zero ambiguous characters and exactly 8 lowercase letters; passphrase mode's default separator/capitalization render correctly, and switching separator/word-count/capitalize/append-number all apply together correctly (9 space-separated parts for 8 words + a 2-digit trailing number, capitalization on/off reflected exactly). - **Hue** (`/apps/hue`) — color converter/harmony/accessibility tool, fourth `Design`-tagged tool after Swatch, Mat, and Bloom. A hand-rolled HSV color picker (SV square + hue slider, both plain layered CSS gradients — no canvas needed, since neither depends on anything but the current hue) drives one canonical `{hue, sat, val}` state; every other format (hex, RGB, HSL, HSV, OKLCH) is a pure `$derived` read of it. `src/lib/hue/convert.ts` holds all the conversions, verified by fuzzing (5,000 random RGB triples round-tripped through HSL and HSV with **zero** rounding error) and, for OKLCH, by checking five reference colors (red/white/black/green/blue) against Björn Ottosson's own published L/C/H values — matched to 4 decimal places. `src/lib/hue/colorblind.ts` simulates protanopia/deuteranopia/tritanopia via the Machado, Oliveira & Fernandes (2009) 100%-severity matrices (cross-checked against an independent transcription of the same dataset from the `colour-science` Python library before hardcoding — same "hand-rolled format needs an independent oracle" lesson as Beacon/Loop/Seal/etc., just applied to sourced-not-derived constants this time) plus a from-scratch achromatopsia grayscale (Rec. 709 luminance in linear light). Sanity-checked the matrices structurally, not just against the source: white and mid-gray come out perfectly unchanged (`r=g=b` preserved exactly) under every matrix, which only holds if each matrix row genuinely sums to ~1 — a transcription typo would very likely have broken this.
  - **A real bug caught by cross-referencing a screenshot against the interaction logic, not by build/check.** The hue slider sits in a narrow, tall column in `.picker-controls`' grid (`1fr 1.4rem` columns) — visually and physically a *vertical* strip. Its drag handler (`huePointFromEvent`) was first written reading `event.clientX` / `rect.width`, copy-adjusted from the SV square's horizontal math without re-deriving it for the slider's actual orientation. It compiled, type-checked, and even *passed* a first Playwright pass that dragged mostly top-to-bottom at a roughly-central X — because the pointerdown's initial X (captured once at drag start) happened to produce a plausible-looking hue change, masking that subsequent vertical movement was doing nothing. Caught by actually looking at the screenshot (the slider handle rendered at a position inconsistent with a horizontal read) and then writing a test specifically designed to catch this class of bug: drag from a fixed X straight down, then from the *same* fixed X straight up, and assert the two results differ — they didn't, confirming the slider was ignoring Y entirely. Fixed by reading `clientY`/`rect.height` instead, inverted (`1 - fraction`) to match the `to top` gradient's bottom-is-0°/top-is-360° convention, and repositioning the handle via `top` instead of `left`. **Lesson worth generalizing: a passing drag-interaction test isn't proof the drag axis is correct — pointerdown alone can produce a plausible result even when pointermove is silently wired to the wrong coordinate.** Test the axis specifically (fixed-X vertical drag, or fixed-Y horizontal drag) whenever a draggable control isn't a simple horizontal bar, and cross-check the rendered screenshot against the interaction code rather than trusting either alone.
  - Format readouts (`.format-row`) and harmony swatches are both click-to-copy with per-item "Copied!" feedback, same pattern as Seal's hash rows and Swatch's palette swatches respectively. `src/lib/hue/harmony.ts` computes six harmony types (complementary/analogous/triadic/split-complementary/tetradic/tints-and-shades) as pure hue-rotations (or, for the last one, a fixed 9-stop lightness ramp) in HSL space — hue is the one axis HSL and HSV share meaning on, so rotating it and converting back to hex needed no cross-model reasoning.
  - Contrast and colorblind-simulation share one foreground/background color pair (page-level `fg`/`bg` state, independent of the picker's own base color, each with a "Use picker color" one-click convenience) rather than being separate, disconnected sections — the real-world question ("is this text/background pair OK") is the same question for both WCAG contrast and CVD simulation, so unifying them under one "Accessibility" mode (paired with "Harmonies" as the other segmented mode) reads better than three independent, uncoordinated sections. `wcagChecks` reuses the exact WCAG contrast-ratio formula already established in Swatch/Beacon (`pickTextColor`'s luminance threshold, `contrastRatio`'s (L+0.05)/(L+0.05) ratio) as its own small independent copy, per the site's standing "small hand-copied formula, not a cross-tool import" convention for things this size.
  - Colorblind prevalence figures next to each label are stated as rough, common-knowledge ranges ("~1% of men," "rare, <0.1%"), not precise citations — same restraint as Ward's crack-time caveat, an order-of-magnitude illustration rather than a number the tool would need to defend.
  - Default picker color is the site's own `--accent` (`#dd4b1f`) rather than an arbitrary color — a small, deliberate identity touch; the picker computes its own initial HSV from that hex once at load rather than hardcoding separately-derived hue/sat/val numbers, so the default can never drift out of sync with the actual accent if it's ever changed.

## Collection strategy

- **Corrected course, same session: combining tools by domain is the actual direction, not something to avoid.** A first pass at this feedback (audit for literal redundancy, conclude nothing overlaps, solve discovery instead of merging) was a misread of the ask — the prompter clarified directly: group by *domain/functionality*, not by "does another tool already do exactly this." Concretely: an **Image workshop** (metadata strip/view, compress, frame/background, crop, palette extraction, favicon export — currently Squish, Bare, Mat, Crest, and Swatch's image-facing side) and a **Color workshop** (harmonies, contrast, gradients, palette-from-image — currently Hue, Bloom, and Swatch's color-facing side) each replacing several single-purpose routes with one tool that has several modes. This is a real information-architecture change, not a discovery-layer fix — noted as the concrete next project below, sequenced *after* the shared component library (next item) since building the workshops on ad hoc page-local markup would just mean redoing them once the components exist.
- **New visual identity, same session: "command line chic" — a neobrutalist/terminal aesthetic, explicitly "retro but modern," not literal CRT nostalgia (no scanlines, no screen-curvature, no faux-degraded glow).** Landed on this after the prompter flagged the bento grid as leaving dead space and asked for retro/pixel/CRT flair with a caveat that it stay "modern and good UI." Concrete implementation, `src/app.css`: headings site-wide now render `font-family: var(--font-mono); text-transform: uppercase` (cascades to every tool page automatically — verified safe by grepping every `<h1-h4>` in the codebase first: with two short exceptions they're all single tool names, so uppercase-mono never had room to overflow anything); borders went from near-invisible (`rgba(..., 0.1)`) to actually visible (`0.22`/`0.4`) so panels read as drawn rather than barely-there; a new `--shadow-hard: 4px 4px 0 0 var(--text)` token (solid, unblurred, offset) is the one deliberately retro affordance, opt-in per element rather than global. Accent shifted from coral-orange toward a deeper "phosphor amber" (`#bc3d0a` light / `#ffa64d` dark) — chosen after checking contrast against the *previous* accent first and confirming it was already borderline (~3.9:1 in light mode, below AA's 4.5 for normal text) so the new color had to do better, not just look different: the shipped values land at 5.2:1+ light / 10:1+ dark, verified with the same relative-luminance formula every other tool on this site already uses. Landing page rebuilt around this language: the file-drop hub gained corner-bracket accents (four `.corner` spans, sci-fi-reticle style) and a hard shadow on hover/drag; the bento grid was fully replaced by a bordered "terminal window" (title bar with dots + a `~/tools` path, hard shadow on the whole frame) containing tools as compact rows grouped under `# TAG` section labels instead of floating cards — rows pack tightly regardless of count, which is what actually fixes "too much empty space" (a grid problem, not a color/font problem). `AppCard.svelte` was rewritten in place from a card to a row (hover/focus inverts bg↔accent, the classic terminal "selected line" — no new component file, since it's still only used by the landing page).
- **Tag taxonomy cut from 12 to 6** (`src/lib/apps.ts`), independent of and ahead of the eventual code-level tool merge: 9 of the 12 old tags had exactly one tool in them (Privacy, Share, Docs, Video, Web, Audio, Motion, Time, and functionally Images), which made the filter row nearly as long as the tool list itself. New set — **Images** (Squish, Bare, Mat, Crest), **Color** (Swatch, Bloom, Hue), **Dev** (Sift, Delta, Claim), **Security** (Seal, Ward), **Media** (Loop, Splice), **Utility** (Beacon, Folio, Ease, Meridian) — sized 2–4 each, and the Images/Color split deliberately mirrors the exact workshop boundary above, so the taxonomy won't need a second rework once the merge actually ships.
- **Shared component library shipped** (`src/lib/components/Button.svelte`, `Panel.svelte`, `Segmented.svelte`, `ToolHeader.svelte`), requested directly for the same reason noted above: every tool page redefined its own `.panel`/`.primary`/`.ghost`/mode-toggle CSS locally, which is why the retro pass could only reach shared tokens (cascade via CSS custom properties) and not the bordered/hard-shadow/press-feedback affordances themselves. `Button` carries the signature interaction: flat at rest, lifts with `--shadow-hard` and a springy overshoot ease on hover, slams flat with a quick scale-down on click — a real tactile press, not a static color swap. `Segmented` covers both the old "mode-toggle" (2 prominent options) and "segmented" (N small chips) patterns via one `compact` boolean rather than two components. **Ward is retrofitted onto all four as the reference pattern; the other 17 tool pages are the same mechanical swap, not yet done** — each one is small (page-local CSS deletion + component imports), but still needs the same per-page Playwright verification every tool here gets, so it's paced as an ongoing sweep rather than one giant PR. Do this *before* building the Image/Color workshops below, so those get built on the shared components from day one instead of more page-local CSS that would need retrofitting again.
- **File-drop hub phase 2 shipped: the dropped file now actually reaches the target tool, no second drop.** `src/lib/fileHandoff.ts` is one-shot module state (`setPendingFile`/`takePendingFile`) — plain, not a Svelte store, since it only needs to survive one client-side navigation and be read exactly once; SvelteKit doesn't reload the module on an internal link click, which is what makes this work without any URL/query-param plumbing. `AppCard` gained an optional `onclick` passthrough so the landing page can stash the file the instant a matched card is clicked, before the browser follows the link. Each of the 10 file-accepting tools reads `takePendingFile()` once at script-init (top-level code, not `$effect` — it doesn't need reactivity, just a one-time read before first render) and feeds it into whatever its own existing intake function already was: `addFiles([file])` for the three batch tools (Squish/Bare/Swatch), plain `loadFile(file)` for the five single-file tools (Mat/Crest/Folio/Splice/Loop), and `loadFile(file, assign)` for the two that needed to say *where* the text lands (Delta → left/"before" side; Sift → also forces Format mode, the natural landing spot for a single JSON file). Verified end-to-end per tool, not just wiring-compiles: real fixture files through the actual click-through-the-hub path (not just calling the handler directly) for all 10, including the two async-decode ones (a real 1×1 PNG for Mat's `createImageBitmap`, a real minimal WAV for Splice's `decodeAudioData` — fake bytes would only prove the wiring reached the function, not that the whole path works), plus a check that visiting a tool directly (not through the hub) never shows a leftover file from an earlier, uncompleted drop.
- **Interaction principle, stated directly and worth keeping: predictability first, but only gate the actions that actually need it.** Live/instant preview is correct and should stay for most of the site — Hue's picker, Bloom's gradient, Swatch's palette, Mat's frame preview are all non-destructive and reversible, and adding a confirm step there would just be friction. The exception is an action that *produces a final artifact with a choice baked in the user didn't consciously make* — Squish auto-compressing (and silently picking an output format) the instant a file landed was the flagged example, and it's shipped now (see Squish's entry above for the redesign specifics). Don't generalize an auto-confirm requirement to tools where instant feedback is the point — Squish needed the gate specifically because "produce a converted/compressed artifact" is its whole job, not because confirm-before-acting is a rule the rest of the site should start following.
- **The standing prompt got a small addition this run**: explicit permission for a run to be about the collection's cohesion instead of always shipping a new named tool. The "keep tools small, don't merge scope" line from that same edit is superseded by the domain-merge correction above — worth remembering as a specific instance of a general lesson: read direction from this repo's owner as intent to investigate, not as a settled architectural stance to defend against.
